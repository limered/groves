## Destination

A hand-off-ready **spec** for a fast, lightweight, read-only git graph viewer (Rust, Windows + Linux): architecture, crate choices, graph layout, data model, refresh model and UX (tiled panes), all decided — nothing left to decide before implementation starts.

## Notes

- Tracker: local markdown in `.wayfinder/`. Children carry `parent: 000`; blocking via `blocked_by: [ids]`; claim via `assignee`; resolution appended as `## Resolution` + `status: closed`.
- Frontier = `status: closed`, no `assignee`, every `blocked_by` closed.
- Research findings live in `.wayfinder/research/<name>.md` (repo has no commits yet, so no research branches).
- Grilling tickets: use skills `grilling` + `domain-modeling`.
- Scale baseline (measured 2026-09-24): BM_AI_Software_Factory = 16.6k commits, 7,140 refs (6,732 tags, 398 remote branches), 3 worktrees, ~80 commits/day, 208 MiB packs. Clarora.AI = 1.5k commits, 236 refs. Design target: 10x Factory (200k commits, 50k refs).
- Both repos contain many `.pack` files without `.idx` — reader must tolerate this.
- Standing decisions from charting:
  - Data access: `gix` read-only; `fetch --all` is the only network op.
  - Every repo/worktree is just a pane; no cross-repo relationship features.
  - Interactions: select commit -> details (message, author, changed-file list, no diff), branch filter, jump to HEAD, tag toggle.
  - Refresh: manual fetch button + periodic background fetch. No filesystem watcher.
  - Tiling: Hyprland-like auto layout inside one app window, keyboard-first, persisted workspace.
  - UI framework: research, then prototype (human judges look).

## Decisions so far

- [Which Rust UI stack can draw a dense graph fast and look GitKraken-nice?](001-ui-framework-research.md): shortlist egui/eframe (+egui_tiles), then iced (canvas + PaneGrid); Slint and pure wgpu ruled out; memory figures unverified.
- [Can gix read commits, refs and worktrees fast and robustly enough?](002-gix-capabilities-research.md): yes, read-only (est. ~0.1 s/17k, 1–3 s/200k commits); topo order is ours to compute; fetch by shelling out to `git fetch --all --prune` (no prompts); release pack mmaps before fetch on Windows.
- [Which lane-layout algorithm fits a 200k-commit graph?](003-graph-layout-research.md): full relayout, pvigier-style straight lanes, est. 30–60 ms at 200k (unbenchmarked); keep lanes stable across refreshes, anchor scroll to SHA.
- [How are thousands of tags and remote branches shown without burying the graph?](005-ref-display-policy-grilling.md): tags hidden by default (toggle, drawn as rectangles); pills filled/outline in lane color, local+upstream merged, `+N` dropdown; filter prunes history to a default ref set (locals, upstreams, worktree HEADs, remotes active in last 14 days), `s` toggles stale branches back in, pattern field instead of a checklist.
- [What should a graph pane look and feel like?](004-graph-pane-look-prototype.md): egui on OpenGL (~150-220 MB, idle CPU under 1%); columns are pills (one per commit, rest under +N), then a resizable graph, then the message with author/date/SHA drawn on top of it; detail panel at the bottom and hidable.
- [How do panes, tiling and workspaces behave?](006-tiling-workspace-grilling.md): one pane per repo with all worktree HEADs marked (duplicates forbidden); dwindle layout, 9 workspaces, OS folder dialog only, fixed Alt keymap (`Alt+.` shows it); layout + repo per pane persisted.
- [What does a pane show by default?](009-pane-default-display-grilling.md): only graph, pills, equal worktree HEAD markers (main name shown) and age lines; commit info on hover, click pins; `d` panel shows union of changed files + messages of all pins; single keys `t s f d m r Esc`; nothing persisted (reverts 005's filter/toggle persistence).
- [When and how does a pane refresh after fetch?](007-refresh-model-grilling.md): 5-min background fetch of all open panes (max 2 parallel, silent auth, backoff on errors, header badge); 10 s ref-snapshot poll + focus re-check for local changes; `r`/`Shift+R` manual fetch with prompts; follow tips at top, else SHA anchor; drop unreachable pins.
- [What is the core architecture and data model?](008-architecture-grilling.md): UI thread + task pool + scheduler thread, per-task repo handles; SoA DAG cache + swappable layout per pane, eager commit info for the ref set; full reload on refresh (MVP); onion crates core/repo/app/bench with a `CommitSource` port; budgets fixed (cold open ≤ 1.5 s at 200k, frame ≤ 8 ms, idle < 1%).
- [How is the performance harness built and run?](010-perf-harness-grilling.md): synthetic in-memory source plus a fast-import on-disk fixture (real repos manual); criterion plus a headless bench bin, idle CPU manual; report-only, on demand, reference is this Windows box.
- [How expensive is the changed-file union for a pin set?](011-pin-diff-cost-research.md): about 1 ms per normal commit in-process (est.), 45-60 ms for a 4k-file commit (measured); merges diffed against the first parent; path sets cached per commit ID, computed on the task pool with cancellation, never on the UI thread.
- [What is persisted, where and in what format?](013-config-persistence-grilling.md): hand-edited global `config.toml` (fetch interval, staleness window; created once with comments) + app-written `state.json` (layout, repos, window geometry, last workspace; debounced atomic writes); portable `<exe>/commit-graph-data/` with OS-dir fallback; DB rejected; corrupt state backed up, bad config falls back to defaults.
- [How is the viewer packaged and distributed?](014-packaging-grilling.md): one portable binary per OS (Windows zip, Linux tarball built with zigbuild against glibc 2.31, Wayland and X11); system git optional (only fetch is turned off without it); OpenGL 3.3 only, clear error otherwise; no updater, no code signing; built locally for now.

## Not yet specified

- Incremental refresh (walk only new commits into the DAG cache) once full reload proves too slow.
- Filtering from inside the interactive graph (e.g. hide/solo a lane from its pill) to replace or supplement the pattern field.
- Tag extras: always-shown tag pattern (e.g. `v*`); where tags of a commit are listed when the dropdown excludes them (detail panel?).
- Theming / GitKraken-like visual language details beyond the prototype.
- CI choice (GitHub Actions likely), whether it builds and publishes releases, and whether bench budgets become gates there (margins, baseline storage); a Linux reference machine.

## Out of scope

- Commit, push, checkout, merge, any write operation (only `fetch --all`).
- Code review / diff viewing.
- Cross-repo relationships (e.g. consumer repo's Factory template version).
- Filesystem watching of `.git`.
- macOS.
- [How does search work?](012-search-grilling.md): search (message/SHA/author) cut from the feature list for now; unclear it will be used in this viewer.
